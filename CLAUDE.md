# FlowSketch (repo name on GitHub: piper5ul/flowsketch; local dir ~/whimsy)

Whimsical-style diagramming app. Sharing (public read-only links, per-user invitations), version history and commenting are wired end to end. Realtime is **done — all four phases** (`docs/realtime.md`): live presence, document sync, per-user undo and offline. An open diagram lives in a Yjs document, `Diagram.data` is a snapshot rendered from it, ⌘Z takes back your own edits only, the top bar reports the connection where it used to report a save, and `y-indexeddb` keeps a copy in the browser so a dropped socket — or a reload with no network at all — costs nothing.

## Commands

- `npm run dev` — Vite on **5199** (not 5173) + Express on 3001 via `concurrently`
- `npm run check` — lint + typecheck + unit tests. Must be green before any commit (pre-commit hook runs it)
- `npm test` / `npm run test:watch` — Vitest (no DB needed)
- `npm run test:e2e` — Playwright; reuses a running dev server locally, starts its own in CI
- `npm run build` — `tsc -b && vite build`; `npm run build:server` compiles the API to `dist-server/`
- `docker compose up -d` — Postgres + MailDev for local dev
- Install with `npm install --legacy-peer-deps` (npm 10.9 arborist bug with vitest's peer set)

## Architecture (read this instead of re-reading the files)

- `src/store/useDiagramStore.ts` — single Zustand store: nodes, edges, tool, defaults, undo/redo. **There are two undo models and the store dispatches between them** (see the undo bullet below): a `Y.UndoManager` in the document when one is bound, the module-level snapshot stacks (`past`/`future`) otherwise. Both are driven by the same call sites: **an action that mutates nodes/edges calls `pushHistory` first, which pushes a snapshot for an unbound diagram and marks an undo boundary for a bound one.** The stacks are kept out of the store so they are never serialized; `canUndo`/`canRedo` mirror whichever history is in force. Discrete edits (`updateNodeData`, `updateEdgeData`) push, but skip no-op patches. A pointer drag pushes once via `beginInteraction()` and then uses a transient action (`updateEdgeDataTransient`, `moveNodesTransient`, `reconnectEdgeEndpoint`). `nudgeSelected` coalesces entries within 500 ms. `loadDiagram` resets history.
- **Undo is per person for a bound diagram, and that is the `Y.UndoManager` in `binding.ts`.** It is scoped to `trackedOrigins: {LOCAL_ORIGIN}` — the one origin every local transaction carries — so ⌘Z reaches back through *your* edits past a collaborator's and can never take theirs back; and because undoing is itself an edit, it undoes on their screen too. **`captureTimeout` is infinite on purpose**: what splits one entry from the next is the store, never a clock — `pushHistory` → `DocumentHistory.beginEntry()` → `stopCapturing()`, plus one more boundary the binding opens at the first *transient* frame of a gesture (the store cannot say, because a drag pushes history on the release). A timeout would have split a drag the user paused in the middle of and would have coalesced nudges on a different rule from `nudgeSelected`'s 500 ms. **`meta` *is* in the manager's scope, and the viewport is kept out of it by origin rather than by key.** A board's defaults, its thumbnail, its round of voting and its countdown are all things somebody chose and can un-choose, so ⌘Z has to reach them the way it reaches a shape; the camera in the same map is not an edit at all — it is written for the snapshot's sake, is never read back out, and an undo entry for panning would move nothing anybody can see. Yjs scopes an undo manager by *type* and by *origin*, never by key, so `push` writes the viewport in a **second transaction under `viewportOrigin`**, an origin `trackedOrigins` does not carry (`markDirty` treats both as local, or the binding would read its own camera back as a peer's). That is cheaper and less invasive than splitting `meta` into two `Y.Map`s, which would have changed the document format for every board already stored. Selection is not in the document either, so `stack-item-popped` puts it on the ids the undo touched (collected in the map observers, because a `YEvent` refuses to describe its changes once its transaction has closed). `useCollabStore` registers the manager with `setDocumentHistory` for an editor and not for a viewer; the snapshot stacks are what a diagram with no document behind it still uses, and every test of them still passes untouched.
- `src/commands/` — the command registry. `commands.ts` is the one list of everything the app can do (see the read-only note below for the gate it applies on the way out); `registry.ts` matches a `KeyboardEvent` against it (⌘ and Ctrl are one `meta` flag; `event.code` is the fallback when ⌥ or a non-US layout rewrites `event.key`) and formats a binding per platform. A command's `when` gate is what lets two share a keystroke — and what lets ⌘V fall through to the browser's paste listener when our clipboard is empty, so image paste keeps working. The keyboard handler, the `?` cheat sheet (`ShortcutSheet.tsx`), the right-click menus (`ContextMenu.tsx`, driven by each command's `contextMenu` tag; `ITEM_HEIGHT` decides *where* it opens and is only an estimate — a title that wraps onto a second line makes the menu taller than that — so what keeps it on screen is a `maxHeight` of the room left under that corner, with the list scrolling inside it) and the ⌘K command menu (`CommandMenu.tsx`; `src/lib/commandMenu.ts` ranks by title match with the recently used first, recents kept as a per-browser preference) are all generated from it: add a shortcut in one place, not five. The menu offers exactly what each command's `when` allows against the canvas's own context, so it never disagrees with the keyboard.
- **Quick-add is two offers of one thing, and `canQuickAddFrom` (`nodeKinds.ts`) is what keeps them the same offer.** The pointer's is the four `.quick-add-btn`s around a hovered shape (`ShapeNode`); the keyboard's is `quickadd.right/left/down/up` — **⌥ plus an arrow**, Whimsical's key and the one combination the arrows had left (a bare arrow nudges, ⇧ nudges further, ⌥⇧ aligns), gated on exactly one selected node that predicate allows. It withholds a text shape, a mind-map node (Tab and Enter are how a map grows), a floating arrow's 1×1 endpoint, and anything that is not a drawn shape. **The command opens the new label and the button does not**: ⌥→ is the middle of type-⌥→-type, where a click leaves the pointer somewhere else — so `setEditingNodeId` is the command's, not `addConnectedShape`'s, which is otherwise unchanged (it still copies the source shape's style rather than the board's default). Neither carries a `contextMenu` tag; the ⌘K menu lists them as it lists everything.
- **The left rail must never grow past the board.** It is a dozen 40 px buttons in a column and its height is a fixed cost a 1280×700 laptop window nearly spends in full, so `LeftRail` bounds it (`max-h-[calc(100%-2rem)]` on the wrapper, `overflow-y-auto` on the stack) and `index.css` tightens the gaps and padding under `@media (max-height: 800px)` (`.rail-stack` / `.rail-divider`). Scrolling is the reserve, not the plan: at 700 px the compact spacing alone fits, which `e2e/polish-select.spec.ts` asserts by measuring the rail's own overflow and every button's box. **No tool is dropped or folded away to make room** — the popovers are Radix portals, so a scrolling rail still opens them over the canvas — and the stack carries `role="toolbar"` with a name for the reason `FloatingToolbar` does: several of its buttons share a label with one elsewhere.
- `src/lib/selectionFilter.ts` is the pure half of the toolbar's **Filter selection** (`FilterSelectionMenu.tsx`, offered for a multi-selection): the kinds and fills present in the selection with counts, and the ids that match one; `narrowSelection` in the store applies it with no history entry, as a click would.
- **Three precision gestures** live in `Canvas`'s held-key state: ⌘ held sets the store's `snapOverride` to `'guides'` and ` to `'all'` (`onNodesChange` skips the alignment snap for either, and `snapToGrid` is withdrawn for the second), and ⌥ over a shape while exactly one other is selected mounts `MeasureOverlay` (`src/lib/measure.ts` is the pure gap geometry; `.measure-overlay` is on the export exclusion list).
- `src/components/Canvas.tsx` — React Flow wrapper. Its keyboard `useEffect` is now three lines: skip typing targets, ask the registry for a command, `preventDefault` and run it. The command context (store, viewport, both clipboards, hold-to-pan, the sheet) is built there with `useMemo`; the copy/paste and copy-style clipboards are refs, since neither belongs in a saved diagram. The right mouse button opens the context menu, so `panOnDrag` is the middle button only.
- **Containers are nodes other nodes hang off, and `src/lib/nodeTree.ts` holds the three invariants that come with that.** A `group` (`src/nodes/GroupNode.tsx`) is invisible unless pointed at or selected — a way of handling shapes, not a mark on the diagram, which is why it needs no exclusion from the export; a `frame` (`FrameNode.tsx`) is a titled section painted from the theme tokens and *is* part of the drawing — unless the user picked it a colour, in which case it wears a toned-down `color-mix` of that fill and stroke over the panel, the way Whimsical's sections do (the toolbar offers a frame the palette and nothing else: `colourableNodes` in `FloatingToolbar`). Both carry an ordinary `ShapeData` and live in the same array as every shape: **`type` tells them apart, never the data** (`isGroupNode` / `isFrameNode` / `isContainerNode` in `nodeKinds.ts`) — a container's fill and stroke are both `transparent`, which is exactly what `isAnchorNode` reads, so asking the data would confuse a group with a floating arrow's endpoint. The invariants: (1) **a child's `position` is relative to its parent**, so anything reasoning about where a node *is* goes through `absolutePosition` — that is why the alignment-guide snap, the floating toolbar's anchor and the arrange commands all work in board coordinates and convert back on the way in; (2) **a parent must precede its children in the array**, restored by `sortParentsFirst` at the end of every z-order action — it is the identity on a diagram with no containers, so an ordinary board reorders exactly as it always did; (3) **a `parentId` must point at a node that is really there**, or React Flow throws instead of drawing the board — `normalizeParentage` runs in `loadDiagram`, the one door every diagram comes through, because `Diagram.data` is free-form JSON. Membership is set three ways and only three: a group is joined and left with `groupSelected` / `ungroupSelected` (⌘G / ⌘⇧G), a frame is put *around* a selection by `wrapSelectionInFrame` ("Wrap in frame" on the node menu — Whimsical's "Wrap in section"; one shape is enough, and the frame is sized to the contents plus `FRAME_PADDING` and `FRAME_TITLE_INSET`), and a frame is otherwise joined by where a drag ended — `Canvas`'s `onNodeDragStop` hands the dragged ids to `reparentByPosition`, which picks the **innermost** frame whose box holds the node whole. Deleting, duplicating and copying all act on the whole subtree (`subtreeIds`), so a container is one thing on the board. `parentId` and `extent` are serialized (only when set, so an old diagram's JSON is unchanged) and no migration was needed: the v0 step only fills in a *missing* `type`.
- **⌘-click reaches inside a group, and `src/lib/deepSelect.ts` is the whole rule.** `deepSelectTarget(nodes, clickedId, modifiers, connectorSelected)` answers with the id a click should leave selected on its own, or `null` to leave the click to React Flow; `Canvas`'s `onNodeClick` calls `selectOnly` with it, which is enough because React Flow has already applied its own selection change by the time a click handler runs. **The rule is: ⌘ (Ctrl elsewhere) alone, on a node with a *group* ancestor, with nothing selected but that node's own ancestors.** The conditions are not decoration — ⌘ is React Flow's default `multiSelectionKeyCode` (`Meta` on a Mac, `Control` otherwise) and `Canvas` does not override it, so deep select is only allowed to speak where a multi-selection is not being built; the moment a second thing is selected the answer is `null` and ⌘ means what it always meant. ⇧ and ⌥ are excluded for the same reason (box selection and the measure overlay), and a selected *connector* blocks it too — that is the one fact the helper cannot read off `nodes`, hence the flag. A **frame** is not reached into: clicking a shape inside one already selects the shape, since a frame is part of the drawing rather than a box around a handful of shapes. Note what this does **not** change: a plain click on a group member already selects that member, and a member is dragged on its own — a group is "one thing" when grabbed by its margin, and making a click select the group would split click from drag.
- **A table is a node type of its own, and its box is its grid.** `src/nodes/TableNode.tsx` draws a real `<table>` inside the node; `src/lib/table.ts` is the pure half and `data.table` (`TableData` — `columns[].width`, `rows[].cells`, `header`) the representation, an optional field on the same `ShapeData` every node carries. **`type` tells it apart, never the data** (`isTableNode`): a table's data is a *rectangle's*, fill and stroke included, because that is what tints its header and draws its rules — so asking the data would answer "rectangle", which is also why the toolbar's shape swapper and `setSelectedShapeKind` exclude it on the type. It is **not** a container: nothing hangs off it, so `isContainerNode` stays the two it was. **The node's `width`/`height` are derived** — `tableSize` = Σ column widths × rows × `DEFAULT_ROW_HEIGHT` — and `withTableSize` re-boxes the node inside every write that can touch the grid (`updateNodeData`, `updateNodeDataTransient`, `addTable`, `loadDiagram`), so connectors, alignment, the minimap and the export bounds go on reading a node's box and knowing nothing about tables; no `NodeResizer` is offered and "match size" skips a table the way it skips a locked node. **Every function in `table.ts` returns the table it was given, by reference, when nothing would change** — that is what makes an unchanged cell cost no ⌘Z (`isNoOpPatch` is `Object.is`) and what lets the cell editor commit on Tab *and* on the blur that follows it. Editing: click a cell to put the cursor there (`activeTableCell` in the store — a cursor, not an edit, and what the toolbar's "Add row" acts on), double-click or **Enter** to open it (Enter arrives as the ordinary `edit.editText` command setting `editingNodeId`, so there is still one list of shortcuts), Tab / ⇧Tab / Enter / Escape to move and stop; Tab past the last cell adds a row **in the same patch as the cell it just committed**, so that is one ⌘Z. **An open cell sets `editingNodeId` too**, and that is not decoration: it is what the rest of the app means by "a text editor is up", and without it a letter typed into a cell would still reach `Canvas`'s mind-map escape hatch and drop a map on the board (`mindmap.addRoot` is `m`, gated on nothing being edited). `TextFormatBar` skips a table for the same reason the floating toolbar does — a cell's typography is the grid's, not one label's, and half a bar would be worse than none. A column resize is the usual drag shape: `beginInteraction` then `updateNodeDataTransient` per frame. Colours follow the *frame's* idiom rather than a shape's — panel and rule from the theme, with a `color-mix` of the user's fill tinting the header — because a table is structure; exports pin the light theme, so that is not dark. `parseTableText` is what a paste comes through: a Markdown pipe table (the `|---|` rule is what says "header"), then TSV, then CSV, with a single line, a ragged block and a one-column list all refused, and **the plain-⌘V listener tries Mermaid first, then tables** (`Canvas`'s paste effect; `clipboard.pasteAsTable` is the menu item). `search.ts` finds a table by any cell, still at most one hit per element. Cell text is plain: **Markdown inside a cell is a follow-up**, deliberately, so a cell says what was typed. For the Yjs binding a table is one node whose `data.table` changes as a whole per cell edit — one entry per node, so two people in different cells of the same table is last-writer-wins per table rather than per cell, which is the same rule two people on one shape already get.
- **Wireframes are one node type holding fourteen sketches, and the palette is the point.** `type: 'wire'` (`isWireNode`, read from the `type` like every other kind — a wire node's data is a *rectangle's*, so asking the data would answer "rectangle"), `data.wire` is `{ component, props? }` (`WireData`), and `src/nodes/WireNode.tsx` is one `switch` on the component: browser (title bar, three dots, an address pill), phone (rounded bezel, notch, inset screen), card (thumbnail band over two text bars), button, input, dropdown (chevron), checkbox, toggle, heading, paragraph, link, image (the crossed rectangle), avatar, divider. **One node type and not fourteen** because they differ in what they *draw* and not in what they are: fourteen React Flow types would be fourteen copies of the same resizer, handles and label editor, and adding a fifteenth is a case in that switch plus a row in `WIRE_DEFAULTS`. `src/lib/wireframe.ts` is the pure half (the component list, labels, `WIRE_DEFAULTS` sizes and minimums, `hasLabel` / `labelPlaceholder`, the palette constants, `wireTint`, and `wireComponentOf`, which narrows the free-form JSON — a component name this build cannot draw renders nothing, as `InkNode` does for a stroke with no points); `src/lib/wireIcons.tsx` is the icon table, kept out of it because `wireframe.ts` is reached from `src/types.ts` and so is compiled by the server. **The colours are the fixed wireframe palette, not the user's fill and stroke** (`WIRE_STROKE` `#9EADBA`, `WIRE_FILL` `#EAEFF4`, `WIRE_FILL_SOFT` `#F7F9FA`, `WIRE_TEXT` `#4B5C6B`, 1.5 px, 4 px radii) — Whimsical's rule, "toned down, more transparent colors by design… this helps keep wireframes semantic". A picked colour is mixed in at 30% (40% on the outline) through `wireTint`, and **the trick is that `addWire` stores the palette entry itself in `fill`/`stroke`**: the base of every mix is the colour the part would have worn anyway, and mixing a colour with itself is the identity, so the renderer mixes unconditionally and there is no untinted branch — and the two colours are deliberately not both `transparent`, which is what `isAnchorNode` reads. `kindOf` (`defaultStyle.ts`) answers `null` for one, both ways round: ⌘⇧D must not stamp the wireframe grey on every box, and the board's default must not repaint a wireframe. **The label is `data.label`** exactly as a shape's is, which is what makes search, typography, Markdown (paragraph only), export and the document work with no special case — the toolbar therefore splits `styleableNodes` into `textableNodes` (adds a labelled wire) and `styleableNodes` (drops every wire: a fixed palette has no Filled/Outline, corner radius or shadow to offer). `canSwapShapeKind` refuses one on its `type` beside the table and the stroke. **The tool is one `Tool` value, `'wire'`, with `wireComponent` beside it in the store** rather than fourteen tool ids: fourteen would be fourteen `TOOL_COMMANDS` rows for keystrokes none of them has, and every reader of `Tool` would parse a prefix instead of comparing a name. **W opens the rail's picker rather than arming anything** (`tool.wireframe` → `ctx.ui.openWireframes`, whose open state is `Canvas`'s and is passed down to `LeftRail`, the `openShortcuts` shape) — there is no single "wireframe" to place, and the rail is one button with a popover because it is already as tall as a laptop window can hold. `addWire` is one history entry: it selects the node and, for a component that says something, opens the label. `selectionFilter.ts` buckets a wire node by its **component** (`FilterKind` = a `ShapeKind` or `wire:<component>`, the prefix keeping `image` the shape apart from `image` the placeholder) — filing every button under "Rectangle" would be worse than not offering them. **`browser` / `phone` / `card` are not containers** in this build: nothing hangs off them through `parentId`, so `isContainerNode` stays the two it has always been, and making them own what is dropped on them is a follow-up. No migration: `ShapeData.wire` is absent on every node of every older diagram (noted in `diagramMigrations.ts`'s header).
- `src/lib/arrange.ts` — pure geometry for align / distribute / match size, over plain `{id,x,y,w,h}` rects. The store's `alignSelected` / `distributeSelected` / `matchSizeSelected` map the selection onto it and commit the result through one shared path that skips locked nodes (they still count towards the geometry, so a locked node is the anchor) and pushes **no** history entry when nothing would move. **The rects are board coordinates:** `selectedRects` builds them with `absolutePosition` and `commitArrangedPositions` turns each result back into an offset from the node's parent before storing it, so a framed shape can be lined up with one outside the frame and the JSON still holds the parent-relative form React Flow reads. **A selected node whose ancestor is also selected sits the command out** — moving a container already moves its contents, so arranging both would move the descendant twice — which is also why a frame plus only its own children is not a selection to arrange. Distribute equalises gaps between *edges*, and match size uses the largest node as its reference — selection order is not tracked anywhere. Both are bound in the registry (⌥⇧ + arrow / H / V to align, ⌘⌥⇧H / ⌘⌥⇧V to distribute) and gated on a real multi-selection.
- **Auto-layout is `src/lib/autoLayout.ts` plus one store action, and the layout engine is code-split.** "Lay out vertically / horizontally" (`arrange.layoutVertical` / `arrange.layoutHorizontal`, no keystroke — Whimsical has none either, and the ⌘K menu and the node context menu list a command whether or not it carries one) redraws a **connected** selection as a layered flow. The lib is pure and structural like `arrange.ts`: `layoutMembers` applies the same outermost-selected rule (a selected node whose ancestor is also selected sits it out; a container is laid out as **one box**, since its contents already travel with it) and drops a floating arrow's invisible endpoints and anything React Flow has not measured; `layoutGraphFor` turns members plus **only the connectors joining two of them** into ELK graph JSON, sized with `boardRect` so a framed shape is measured on the board; `applyLayout` translates the answer so its top-left lands on the selection's own bounding-box corner (**the drawing must not jump**), converts back to parent-relative positions the way `commitArrangedPositions` does, and rounds to whole pixels; `canAutoLayout` is the `when` gate — two members and at least one connector between them, because two unconnected shapes are not a flow. `layoutOptions` is `layered` + `NETWORK_SIMPLEX` (it centres a chain on one line exactly, where the default `BRANDES_KOEPF` averages and leaves a shape two thirds of a pixel out) + 48/64 spacing + `ORTHOGONAL` routing, whose *sections* are thrown away: a connector is drawn by `connectorPath.ts` against the shapes' live positions, so frozen points would be wrong the moment anything moved. **Connectors between members are re-pinned**, `bottom → top` going down and `right → left` going across, with `waypoints: []` through the same key "Reset route" writes — an `EdgeAnchor` keeps whichever side the user drew on until something says otherwise, and a layout is that something; an edge reaching outside the selection is left alone. `useDiagramStore.layoutSelected` is the only async action in the store: `src/lib/elk.ts` reaches elkjs (1.4 MB, EPL-2.0) through a **dynamic `import()`** so it is a separate chunk fetched on first use, and `vite.config.ts` names it in `optimizeDeps.include` only so the dev server pre-bundles it instead of full-reloading mid-session. The whole result — positions and edge patches — is **one** `pushHistory` and one `set`; the state is re-read after the `await` (the board can move on), locked nodes stay put but still count towards the graph exactly as in `alignSelected`, and a second identical run costs no history entry.
- **"Paste as" is two commands, two pure modules and one rule about undo.** `clipboard.pasteAsStickies` and `clipboard.pasteMermaid` (`contextMenu: 'pane'`, no keystroke, gated as edits) read the *system* clipboard with `navigator.clipboard.readText()` — asynchronous and permissioned, which is why neither has a `when` beyond editability: what the text is cannot be known until the user has already asked, so a refusal ("Clipboard access was refused") and a miss ("That isn't a Mermaid flowchart") are toasts rather than a menu item that was quietly absent. Where the result lands is `ctx.dropPoint()` (`Canvas` builds it): the board point the **pane's** right-click menu was opened at, or the middle of the view for the ⌘K and ⌘V paths — kept in its own ref rather than sharing the comment anchor, which the *node* menu also writes. `src/lib/pasteAs.ts` is the list half (`linesOf` strips `-`/`*`/`•`/`1.`/`[ ]` and drops blanks; `stickyGrid` lays rows of `ceil(sqrt(n))` capped at 5 with a 24 px gap from the origin) and `src/lib/mermaid.ts` the flowchart half — a scanner, not a grammar, and no library: statements are split at the top level so an arrow *inside* a label is text, node shapes come from a table of bracket pairs, and the inline link-label form (`-- text -->`) deliberately requires an arrowhead or `A --- B --- C` would read `B` as a label. Its own header comment is the list of what it does and does not cover; `subgraph` is flattened and anything without a `graph`/`flowchart` header is `null`. **`pasteMermaid` is one undo step across an `await`**, and that is the whole reason it does not call `layoutSelected`: `pushHistory` is the undo *boundary*, so one boundary is opened, the shapes are `set`, and the layout `set` that follows the ELK round trip lands inside the same entry. The shared half is `layoutSelectionPatch` (module-level in the store), which is `layoutSelected` minus its `pushHistory`. The initial placement is `stackAlong` — a plain column or row whose bounding-box corner is the origin — because `applyLayout` anchors its answer to that corner, which is what makes the finished flowchart arrive where the user clicked; `BT`/`RL` are laid out as `TB`/`LR`, since reversing the flow would mean reversing every connector too. **Plain ⌘V pastes Mermaid as well**: the `clipboard.paste` command's `when` withdraws it when nothing of ours is copied, the keystroke falls through to `Canvas`'s paste listener, and that listener now offers the text to the parser after the image branch. Text that is not a flowchart is untouched, so pasting prose behaves exactly as it always did — pasting a *list* stays the menu item's job.
- **A sequence diagram is ordinary shapes and connectors, and `src/lib/sequenceLayout.ts` is the ladder.** There is no node type, no edge renderer and no migration. A **participant** is a `rectangle` (160×48, board default style) in a row across the top with an 80 px gap; a **lifeline** is a dashed `straight` connector from that rectangle's bottom to an invisible **1×1 anchor** far below — the floating-arrow hack (`isAnchorNode`), which is why nothing had to be drawn, exported or excluded for it; a **message** is a `straight` connector between two more anchors, one on each lifeline at the message's own height, carrying the text as its label with Mermaid's head and line style as `endArrowStyle` / `strokeStyle`. A self-message is one lifeline's two anchors 24 px apart with **two waypoints** pushing the polyline out to the right and back (an elbow between two points on one vertical line is the router's least defined case). **Every anchor is a child of its participant** (`parentId`, parent-relative position), and that one decision is the whole of "drag a participant and the column follows": React Flow moves children with their parent, `subtreeIds` makes delete and copy take the column, and `sortParentsFirst`'s invariant is satisfied by emitting the participants first. Messages step down by 48 px from 40 px below the row, on a **running cursor** rather than `index × gap` — a self-message takes two rungs, and stepping by the index would draw the next message through it; the lifelines reach 40 px past the lowest endpoint. What each piece *is* is `ShapeData.sequence` / `ConnectorData.sequence` (`{role, participant, index?}` / `{kind, index}`), a label for later tooling that nothing reads to draw — hence no migration step, and hence the one cast in `resolveDefaultStyle`, since the two share a key and neither whitelist admits it. `parseMermaidSequence` (the second half of `src/lib/mermaid.ts`, a line scanner rather than the flowchart's statement scanner) reads `sequenceDiagram`, `participant X as Label` / `actor X`, participants nobody declared in first-mentioned order, and the eight arrows `->>` `-->>` `->` `-->` `-x` `--x` `-)` `--)` (a doubled dash is dotted; `>>` and `x` are filled heads); **activation, `Note`, and the `loop`/`alt`/`opt`/`par` blocks are parsed and skipped**, with the messages inside a block read as ordinary ones. Each parser answers `null` for the other's source, which is what lets `clipboard.pasteMermaid` — now titled "Paste Mermaid (flowchart or sequence)" — offer the text to both, and `Canvas`'s ⌘V listener try sequence → flowchart → table. `pasteSequence` is synchronous (the geometry is exact; there is no ELK round trip) and is one `pushHistory` and one `set`, selecting the participants. **Deliberately not done:** activation boxes, notes and blocks; and no "Add message" command — a message is added by re-pasting or by hand.
- Text formatting lives in one presentational `src/components/TextFormatControls.tsx` (value + onChange), rendered both by `TextFormatBar` (one label being edited; translates patches onto a connector's `label*` keys) and by `FloatingToolbar` — where it is now **behind a `Text ▾` popover** rather than spread across the bar, still driving the whole selection through `updateSelectedNodesData`, which skips `shape: 'image'` nodes. Its `target` prop is what tells a shape's label from a connector's: a connector's carries size, bold and italic only, and its size is still one of the three names rather than a number of px.
- **`src/components/FloatingToolbar.tsx` shows about ten buttons, not twenty-two, and the rest are nested.** A shape reads left to right as `Text ▾` (the controls above), colour, shape swap, **Filled / Outline**, `Arrange ▾`, the sliders popover, link and delete; a connector as colour, the three kinds, `Line ▾` (stroke style over stroke width — six buttons that were half the bar), both arrowhead pickers, add-label and delete, with "Reset route" *rendered* only when the edge has a waypoint to reset rather than greyed out. Nothing was removed, only folded away, and no keyboard shortcut moved — those live in `src/commands`. `ArrangeMenu` is the one "arrange" popover: z order and group/ungroup/lock always, align / distribute / match size / lay out added when more than one node is selected (the last two disabled — not hidden — until the selection is one they could act on). The bar carries `role="toolbar"` with a name, because several of its buttons share a label with the rail's tools ("Text" opens typography here and picks the text tool there) and a name is what tells them apart in a test.
- `src/nodes/ShapeNode.tsx` — one component renders all 15 drawable shape kinds. The nine **clip shapes** (diamond, triangle, hexagon, parallelogram, document, cloud, star, callout, arrow) are a single filled `<path>` taken from `src/lib/shapePaths.ts` — every outline is drawn in a `viewBox="0 0 100 100"` and stretched to the node's box with `preserveAspectRatio="none"` + `vectorEffect="non-scaling-stroke"`, so a path there is a proportional description and never a pixel one; adding a kind means adding a path, not a branch. Cylinder keeps its own multi-part SVG (its ellipse cap does not stretch like the rest); everything else is a CSS box. `isClipShape` is what tells the two apart. Icons and labels for every kind live in one table, `src/lib/shapeIcons.tsx`, read by the left rail and by the floating toolbar's shape swapper (`setSelectedShapeKind`), so a shape cannot wear two faces. Text editing is a `contentEditable` div committed on blur. **A label is stored as typed and rendered as Markdown when not being edited** (`src/lib/markdown.ts`, pure: `# ` headings, `- ` bullets, `1. ` numbers, `[ ] `/`[x] ` checklist items, inline bold/italic/code; `MarkdownLabel.tsx` renders the block tree) — editing shows the source so the markers can be reached, search and export see plain text, and a plain label never pays for a parse (`hasMarkdown` first). **A label's box is not the node's box:** `textInset(kind)` (`shapePaths.ts`) says how far in from each edge a silhouette's text has to sit — as proportions of the node, resolved against its real size in ShapeNode, because a percentage padding in CSS resolves against the *width* on all four sides. `fontSize` is a number of px read through `resolveFontSize` (`src/lib/text.ts`), which also still answers for the `'small'|'medium'|'large'` older diagrams hold — that is why the scale needed no migration. `textColor` overrides the fill's auto-contrast, and `opacity`/`shadow` go on the wrapper (a silhouette casts its shadow with a `drop-shadow` filter, having no box to trace) while `cornerRadius` goes on the box, for the two kinds `canRoundCorners` allows.
- **A shape carries two colours and draws one of them: `fillStyle` says which, and `src/lib/shapeStyle.ts` is the whole decision.** `'filled'` — what an absent field means, so no diagram needed migrating and none was — paints `fill` with **no border at all** and rests the shape on a soft shadow instead (`SHAPE_RESTING_SHADOW`, or the `drop-shadow` equivalent on a silhouette's `<svg>`, kept off the wrapper so the label is not shadowed and the user's own bigger `shadow` still composes over it); `'outline'` paints white and draws `stroke` around it at 1.5px. Neither rewrites the stored pair, so the toggle is lossless and the palette still hands out both. `shapePaint` is where ShapeNode reads it, and it overrides the field for the two kinds that answer for themselves: **a floating arrow's anchor stays invisible** (`isAnchorNode` — a white box there would be a speck nothing selected) and a text shape never gets a background it did not ask for. `hasRestingShadow` withholds the shadow from those two, from an outline shape (its border does that work) and from a sticky note (which casts a heavier one of its own). The label's contrast is decided against what is *painted*, so an outline shape takes dark text however deep its stored fill is; the default swatch is `white` (`#FFFFFF` / `#CBD5E1`), which is why the second, spread-only ring in the resting shadow matters — white on a white board is otherwise nothing at all. The one silhouette that keeps a line when filled is the cylinder: its cap seam survives as `CYLINDER_SEAM`, or a filled one reads as a rounded rectangle.
- **"Save as default style" (⌘⇧D) is a property of the board, and `src/lib/defaultStyle.ts` is the whole of what a style is.** Two whitelists — `pickShapeStyle` (fill, stroke, `fillStyle` and every typography key) and `pickConnectorStyle` (line colour, stroke style and width, both arrowheads, the routing kind) — and `kindOf(node)`, which sorts a node into `shape` / `sticky` / `text` and answers `null` for a container or an image, which have no style to copy. **Nothing but style gets in, and that is a rule about safety rather than tidiness**: `Diagram.data` is free-form JSON and the document is written by other browsers, so a `defaults` carrying `imageSrc`, `locked` or `label` would stamp somebody's picture, lock or words onto every shape drawn after it — hence `sanitizeDefaults`, run at all three doors (`migrateDiagramData` on a stored row, `docToDiagramData` on a rendered snapshot, the binding's `pull` on a peer's write). **Two layers, session over board:** `defaults` in the store is the saved one and is serialized; `lastStyle` is "the colour this tab last used", which is what carries a picked swatch to the next shape the way Whimsical's quick-add does, and is never saved, never shared and cleared by `loadDiagram`. `resolveDefaultStyle` puts the session above the board, and `saveSelectionAsDefault` **clears the session layer for the kind it writes** — pressing ⌘⇧D is the more recent word and must not be overruled by a swatch picked earlier. Every creation path goes through `newShapeData` / `newConnectorData` (`addShape`, `onConnect`, `Canvas`'s `createShapeWithConnector`, the connector tool's two paths), the connector one regenerating `computeMarkers`; **quick-add is the deliberate exception** — `addConnectedShape` copies the shape it grew out of, because the user is extending *that* row of boxes. Format: `DiagramData.defaults`, optional, **no version bump** (absent means "no board defaults", which is what every older diagram already wants), written by `serializeDiagram` only when set. In the document it is `meta.defaults` — the one thing in `meta` that **is** read back out, unlike the viewport, because a default belongs to the board and a collaborator's next shape has to get it.
- **A mind map is ordinary shapes and connectors wearing a role, and `src/lib/mindMap.ts` is the structure.** There is no new node type and no migration: a shape is a mind-map node when `data.mindMap` says which map it belongs to (`{ root }`, and the root points at itself), a connector is a branch when `data.role === 'mindmap'` (source = parent → target = child), and both fields absent is what every diagram written before this already means (noted in `diagramMigrations.ts`'s header alongside `fillStyle`). **Child order is the order of the `edges` array** — it is serialized, it survives the document, and it is what `parentEdgeIndex` splices into when a sibling is added above or below, so there is no `order` number on a node for two people to renumber at once. **`collapsed` is the diagram and `hidden` is the screen:** folding sets `collapsed` in the data, and `deriveMindMapHidden` (the store) recomputes React Flow's `hidden` at every door a board comes through — `loadDiagram`, the binding's `pull`, every mind-map action — because `serializeNodes` writes no `hidden` key and a stored one would be a cache of what was on somebody else's screen. The layout is **hand-rolled and synchronous** (`layoutMindMap`: root anchored on its own absolute position, siblings stacked 40 px apart, parents centred on their children, levels 80 px apart, a folded subtree taking no room and getting no position at all) rather than ELK's `mrtree` through `src/lib/elk.ts` — the whole gesture is type-Tab-type, and a layout that lands after a 1.4 MB chunk has been fetched is one the typist has already typed past. The store actions (`mindMapAddRoot` / `AddChild` / `AddSibling` / `AddParent` / `ToggleCollapse` / `AddChildren` / `Relayout`) are **one `pushHistory` and one `set`** each, node + branch + layout together, and each ends by selecting the new node and opening it for typing. Dragging one takes its subtree: `subtreePositionChanges` adds a change per descendant to the drag's own, so the snap, the history boundary and the binding's transient hold all see the one gesture they already understand (a board with no mind map on it pays one `some()`). **The keystrokes are shared, and that is settled twice**: `mindmap.addSibling` (Enter) and `mindmap.addChild` (Tab) are declared *before* `edit.editText` with strictly narrower `when`s (one selected node that is *also* a mind-map node), and `Canvas`'s keyboard handler lets a `mindmap.*` command — and only that — through from inside an open label, committing what has been typed first. That second half is why `ShapeNode`'s blur commit now only closes the editor while it is still its own: the next node is already open by then. Follow-ups deliberately left out: deleting a node leaves its children stranded rather than taking the subtree, and a node dropped near another does not re-parent onto it.
- **A freehand stroke is a node of its own (`type: 'ink'`), and `src/lib/ink.ts` is all of its geometry.** `InkNode.tsx` is one `<path>` in an `<svg>` filling the node; `data.ink` is `{ points, width, kind }` with the **points relative to the node's top-left** (like every child's position) and the node's box their bounds grown by half the pen — a tight box would clip half the line and would be *zero-high* for a horizontal stroke, which React Flow can neither select nor resize. **The colour is `data.stroke`**, an ordinary `ShapeData` field, which is the whole reason the palette, the swatch defaults and ⌘⇧D work on a stroke with no special case; `fill` is `transparent` and `shape` a rectangle nothing draws, so `isAnchorNode` — which needs *both* colours transparent — cannot mistake one for a floating arrow's endpoint. `ink` is optional and absent everywhere else, so **no migration was needed** (noted in `diagramMigrations.ts`'s header beside `fillStyle` and `mindMap`). The pure half: `simplify` (Ramer–Douglas–Peucker at 0.5 px — a pointer reports every frame, and each sample would otherwise go into the Yjs document), `inkBounds`, `inkPath` (a Catmull-Rom spline through the samples, reusing `catmullRomToBezier` from `connectorPath.ts`: it interpolates, so the line passes through where the pointer actually went) and `strokeHits`. Width is constant per stroke — a variable-width outline would be a *filled polygon* and a second answer to what a stroke's colour and opacity mean — but `InkPoint` carries the pressure anyway, so that is a change of renderer rather than of format. **The stroke scales with its box**: the `viewBox` is the size it was drawn at and there is deliberately no `vectorEffect="non-scaling-stroke"` (what a connector wants and a drawing does not), so a resize needs no rewrite of the points and pushes no history entry.
- **Drawing is a gesture in `Canvas`, and the eraser is the same gesture backwards.** `beginInkGesture` (beside `beginConnectorGesture`, sharing its `window`-listener shape) captures **every** pointer move in flow coordinates — nothing is thinned there, since how much detail is worth storing is `addInk`'s rule — and draws the live line through a `ViewportPortal` with the same `inkPath` and the same colour (`newInkStroke`) the committed node gets. `addInk` is one `pushHistory`, and it refuses a press that never travelled (`MIN_INK_POINTS`, asked of the **raw** samples: a straight line across the board is two points once thinned and is certainly a stroke). The eraser deletes whole strokes it crosses (`eraseInkAt`, hit-tested at `width/2 + ERASER_SLOP_PX`; partial erase is a follow-up) and its `continuing` flag is what makes a whole wipe **one** undo entry — the boundary is opened by the first deletion rather than by the press, so a wipe that erases nothing leaves no entry that undoes nothing. **The three tools are three `Tool` values** (`pen` / `highlighter` / `eraser`) rather than one with a mode, because `TOOL_COMMANDS` and the rail are both lists of tools; they extend `isDrawingTool`, so nothing under the pointer is draggable while a pen is held. **The keys are B / ⇧B / ⇧E, not Whimsical's H / ⇧H / E** — H is this app's hand tool and E its table tool, and moving a key already in somebody's fingers to make room is the wrong trade. The rail keeps them behind one pen button with a popover (the connector button's shape): the rail is a column beside the canvas and a band of three more buttons made it taller than the window. An ink selection gets the palette, the arrange menu and delete and nothing else — it is out of `styleableNodes` in `FloatingToolbar` (no label to typeset, no box to fill or round), out of `canSwapShapeKind` — **which now takes the node rather than its data**, since what disqualifies a stroke is its `type`; the table exclusion the shape swapper carried moved inside it at the same time, so there is one predicate and not three and out of `kindOf` in `defaultStyle.ts`.
- **Floating arrows are a hack:** an edge whose source and target are both 1×1 nodes with `fill: 'transparent', stroke: 'transparent'`. `isAnchor` checks in ShapeNode/Canvas detect these. Don't "fix" transparent fills without checking this. A *sequence diagram's* messages also run between two anchors, but those anchors are children of their participants — `isFloatingArrowEdge` (`nodeKinds.ts`) is what `ConnectorEdge` asks before offering the drag-the-whole-arrow handle, and it says no to any connector carrying a `sequence` tag.
- **A connector is drawn where the user pointed, and stays pinned there.** `src/lib/connectorGesture.ts` is the pure half (`nodeAtPoint` — later nodes win, so the innermost shape in a frame is the hit; `anchorFor` — the nearest point on the outline as an `EdgeAnchor`; `facingSide`), and `Canvas`'s `beginConnectorGesture` is the gesture: with the connector tool, a press on a shape and a release on another makes an edge whose `sourceAnchor` / `targetAnchor` are the outline points nearest the press and the release (side + fraction), the way Whimsical does it; a release on empty board makes a new shape there (`createShapeWithConnector`, which the handle drag's `onConnectEnd` shares), and a press that never travels `DRAG_THRESHOLD_PX` is still the old click-click flow. The store pins the other two ways an edge is made too: `onConnect` from a side handle and `addConnectedShape` (quick-add) both set both anchors to the sides' middles. **Sides are pinned, not chosen per render:** an edge with anchors keeps leaving and arriving where it was drawn when the shapes move, and only an edge without them (one made through the API) gets `floatingEdgeSides`' automatic sides. The handlers sit on `window` for the gesture's duration rather than capturing the pointer, because capture would redirect the release — and the click the old flow relies on — to the wrapper; `swallowClickRef` is what stops that click from also starting a second connector. **While either gesture is in flight the shape under the pointer is outlined** — `connectTargetId` in the store (transient), set by the tool's `onMove` through `nodeAtPoint` and by React Flow's `useConnection().toNode` for a handle drag, read by every node component as `data-connect-target` and drawn by `index.css` — so a release has a visible answer before it happens. **A short run lifts its label off the line**: `labelLift` (`connectorPath.ts`) moves the pill one pill-height along the path's normal when the run cannot carry the label between its two arrowheads, so the line and both heads stay visible.
- `src/edges/ConnectorEdge.tsx` renders a connector; `src/lib/connectorPath.ts` decides its shape. **`buildConnectorPath(kind, …)` is the one place the three kinds are drawn** — straight, elbow, curved — returning the `d`, the point the bend handle sits on, and a polyline the label is interpolated along. It is pure: the edge component feeds it the anchors, the edge's `waypoints`, and — for an elbow only — the corners from `src/lib/manhattanRouter.ts` (extracted from JointJS, MPL-2.0), which is where those waypoints are threaded as `vertices`. A straight connector is a polyline through them and a curve a Catmull-Rom spline (`catmullRomToBezier`), so a bend lies *on* the path for all three kinds. `cleanPath` absorbs sub-8px kinks from grid snapping. The path also reports its `segments` — one grab handle per run, in path order: dragging one inserts a bend at that index (`insertEdgeWaypoint`) and keeps dragging it (`setEdgeWaypointTransient`), double-clicking a bend removes it (`removeEdgeWaypoint`), and an elbow's drag is held across the run it grabbed. There is no handle at the centre any more — the add-label button sits there and swallows its pointer events, which is also why a handle that would land under the label slides along the path until it is clear.
- Arrowheads are top-level edge fields (`markerStart`/`markerEnd`), regenerated from `data` by `computeMarkers` (`src/lib/edgeMarkers.ts`, re-exported from the store). Persisted JSON stores both. `updateEdgeData` / `updateSelectedEdgesStyle` regenerate them whenever a patch touches `stroke`, `strokeWidth`, `startArrowStyle` or `endArrowStyle`.
- **Each end wears one of eight `ArrowStyle`s** (`none` / `arrow` / `open` / `circle` / `diamond` / `bar` / `halfcircle` / `dot` — Whimsical's set) and React Flow builds defs for only two of them, so `computeMarkers` returns the *id* of a `<marker>` this app defines — React Flow passes a string marker through as `url(#…)` untouched. `src/edges/ConnectorMarkerDefs.tsx` renders one def per distinct style/colour/size across the current edges (`markerDefsForEdges`), through `ViewportPortal`: image export captures `.react-flow__viewport`, so defs mounted outside it would vanish from every exported file. Marker size steps with `strokeWidth` (10/13/17px) rather than scaling with it — `markerUnits="userSpaceOnUse"`. **The regular look is measured, not guessed:** Whimsical's connector at 100% is a 4px `#788896` line, an arrowhead 13px across by 10px deep, elbow corners on a ~12px radius, and a 6px gap between the line and the shape — those are `CONNECTOR_STROKE_PX[2]`, `MARKER_SIZE_PX[2]` with the `arrow` path's 0.77 depth, `BORDER_RADIUS` in `connectorPath.ts`, and `CONNECTOR_STANDOFF_PX` (applied in `ConnectorEdge` through `standoff` in `edgeGeometry.ts`, and skipped for a floating arrow's anchor ends). Change one knowingly; the regular width restyles every diagram saved before widths existed.
- Diagram format is **v2**. v1 carried `startArrow`/`endArrow` booleans; the `v1ToV2` step rewrites them as styles and drops them, so `v0ToV1` no longer touches markers at all. **Marker ids are recomputed on every load, whatever version the payload came in at** (`withCurrentMarkers`, the last thing `migrateDiagramData` does): an id folds style, colour and *size* into a name, the size steps have changed between builds, and a stored id pointing at a def this build no longer renders is an arrowhead that silently vanishes — it also covers an edge that arrived through the API with no ids at all. A stored id is never load-bearing.
- `server/` — Express 5. `router.ts` is the diagram CRUD; `auth.ts` is BetterAuth with Prisma adapter; `middleware.ts` puts `req.user`/`req.session` on the request, typed in `types.ts` by declaration-merging `Express.Request` with `auth.$Infer.Session` — routes read it through `authedUser(req)`, never a cast. `validation.ts` holds the zod body schemas (POST/PUT `/api/diagrams`, POST members, POST versions, the comment bodies) and `threadFilter`, which reads `?resolved=` as `open` unless it says `resolved` or `all`; `rateLimit.ts` the limiter factories (600/15 min on `/api`, 60/15 min on `POST /api/images`, 300/15 min on `/api/shared/*`, 120/15 min on the two routes that write a comment, all skipped when `NODE_ENV=test`). `GET /api/health` is DB-free; `?deep=1` also pings Postgres and 503s if it is down.
- **`server/access.ts` is the one place that decides who may do what with a diagram.** A route never writes `where: { id, userId }` any more: `requireDiagramRole(req, res, minRole, select)` answers `404` when the caller has no access at all (a diagram they cannot see stays indistinguishable from one that is not there), `403` when they can see it but not do *this* to it, and otherwise hands back the columns it was asked for — the access check and the row come out of **one** query, the caller's member row read as a filtered relation. Roles are totally ordered (`owner > editor > viewer`). GET needs viewer+, PUT editor+, version *reads* viewer+, version snapshot/restore editor+, and DELETE / duplicate / star / sharing / member management are owner-only; `starred` is refused on an editor's PUT because it is one column on the row, not a per-user flag. **Every route that answers with a diagram row runs it through `publicDiagram(row, role)`** (same file), which drops `shareToken` for anyone but the owner — doing that by hand is how `GET` came to strip it while `PUT` handed an editor the whole row. Its constraint is `{ id: string; shareToken?: … }`, so a row that never selected the column passes through unchanged and the call still costs a route nothing. `server/sharing.ts` holds both halves of sharing: `sharingRouter` (mounted inside `apiRouter`, so behind `requireAuth`) for `POST`/`DELETE /api/diagrams/:id/share` and the member routes, and `sharedRouter` (mounted by `index.ts` at `/api/shared`, **no session at all**) for `GET /api/shared/:token` and `/:token/images/:imageId` — the token is the whole credential, and the diagram's own JSON is the allow-list for which images it can reach. `GET /api/images/:id` now also serves a non-owner who is a member of some diagram that draws it, which costs one scan of the diagrams shared *with* that user (documented at `memberCanSeeImage`).
- **`server/versions.ts` is version history**, mounted inside `apiRouter` (there is no unauthenticated half: a share token buys a look at the diagram as it is, not at every state it has ever been in). `PUT /api/diagrams/:id` calls `recordVersionIfDue` whenever the edit changes `data` — it snapshots the **previous** `data`+`title`, and only when the newest existing snapshot has aged past `VERSION_INTERVAL_MS` (default 10 min), so an afternoon of 2 s autosaves leaves one row per burst of editing rather than one per keystroke; a rename/star/thumbnail PUT records nothing and does not even read the old JSON back. Retention keeps the newest `MAX_VERSIONS` (default 50) per diagram, deleting the surplus **by id** (a timestamp cutoff would have to guess about rows sharing a millisecond). The prune reads `data` alongside the surplus ids and hands what those snapshots drew to `deleteOrphanImages`: retention is the only moment an image kept alive by history alone can become garbage, and once the row is deleted nothing can say which images it drew. Both the snapshot and the prune are best-effort — logged, never a failed PUT — and so is that cleanup, separately, since by then the rows are already gone. The routes are `GET …/versions` (metadata only, newest first), `GET …/versions/:versionId` (with `data`, for preview; the lookup is scoped by `diagramId`, so another diagram's version is a 404), `POST …/versions` (manual snapshot of the *current* data, ignoring the interval), and `POST …/versions/:versionId/restore`, which writes a `Before restore` snapshot **first** — not best-effort, that one — then overwrites `data`/`title` and answers with `{ id, title, data, updatedAt }` so the client's conflict guard can advance. Every write carries the diagram's `ownerId` in its `VersionInput`, because retention frees the *owner's* uploads even when an editor's save triggered it.
- **`server/comments.ts` is commenting** — threads pinned to a diagram and the messages inside them, mounted inside `apiRouter`, again with no unauthenticated half (a share token buys a look at the board; a discussion needs names against it). **Reading and writing are both viewer+**, which is the one rule here that looks wrong and is not: a viewer is somebody invited to review, and a review they cannot write down is not a review. What a viewer may not do is call a thread settled — `resolved` is editor+, *or* the person who opened the thread. **Editing is narrower than deleting**: only the author may rewrite a comment (putting words in somebody's mouth is a different act from removing them), while the author, the thread's opener and the diagram's owner may delete one. Deleting a thread is the owner or its opener. A thread is anchored **either** to a `nodeId` **or** to an `x`+`y` — exactly one, enforced by a zod `refine` in `validation.ts` because three nullable columns cannot express it in the database — and `nodeId` is not a foreign key, nodes living inside the `Json` column, so a pin outlives the shape it was on and the canvas decides what to draw. A thread is created with its first comment in one nested `create` (an empty thread is never a state the database can be caught in) and **deleting the last comment deletes the thread**, counted *after* the delete rather than reasoned about before it. Every lookup is scoped by `diagramId` as well as by id, so another diagram's thread or comment id is a `404` even for a caller who could read it where it really lives. `GET …/threads` returns threads newest first with their whole conversation nested (a panel that fetched per pin would be a request per pin), oldest comment first, both tie-broken by `id`.
- **`server/folders.ts` is personal filing** — `Folder { userId, name }` and `Diagram.folderId`, one flat level, mounted inside `apiRouter` and **owner-scoped end to end**: a folder has no access list, so `where: { id, userId }` *is* the authorization rule here (the one part of the API that still looks the way everything did before sharing existed), and a folder the caller does not own is a `404`, never a `403` — somebody else's filing is not enumerable by id. `PATCH`/`DELETE` use `updateMany`/`deleteMany` so the scope and the write are one query with no window between them. `folderId` on `PUT /api/diagrams/:id` is **owner-only for the same reason `starred` is** (one column on the row, pointing at a folder only the owner can see), and the id must name one of *their* folders or the route 404s; `GET /api/diagrams` reports `folderId: null` on somebody else's diagram, because naming the owner's folder would leak a label the recipient can neither see nor change. **Deleting a folder never touches a diagram** — the FK is `ON DELETE SET NULL`, so its contents return to the root on their own, and `folders.test.ts` asserts that no route here writes to `Diagram` at all. A duplicate lands in the same folder as its original. Client side, `src/components/FolderSidebar.tsx` is the rail and `src/lib/diagramList.ts` the pure half (`FolderSelection`, `applyFolderSelection`, `countByFolder`): the counts beside the folder names are **derived from the loaded diagram list**, not from `FolderInfo.diagramCount`, so a move updates them in the same render instead of after a round trip. Dragging a card onto a folder row uses HTML5 DnD with a private MIME type (`src/lib/diagramDrag.ts`) — the type is readable during `dragover` where the value is not, which is how a row knows to accept the drop.
- `prisma/schema.prisma` — BetterAuth tables + `Diagram { data: Json, thumbnail (never written), starred, shareToken? @unique, folderId? }` + `Folder { userId, name }` (`@@index([userId])`; cascades from `User`, `SetNull` into `Diagram.folderId`) + `DiagramMember { diagramId, userId, role }` (`@@unique([diagramId, userId])`; the owner is `Diagram.userId` and never a member row) + `DiagramVersion { diagramId, data: Json, title, label?, createdById? }` (`@@index([diagramId, createdAt(sort: Desc)])`; cascades from the diagram, `SetNull` from the author, whose account may go while someone else's diagram lives on) + `CommentThread { diagramId, nodeId?, x?, y?, resolved, createdById }` (`@@index([diagramId, resolved])`) and `Comment { threadId, authorId, body, editedAt? }` (`@@index([threadId, createdAt])`) + `DiagramDoc { diagramId (pk), state: Bytes, updatedAt }` (the Yjs document, cascading from the diagram; its *existence* is the answer to "is this diagram edited live?") + `DiagramImage { diagramId, imageId }` (`@@id([diagramId, imageId])`, `@@index([imageId])`; cascades from both sides — the index of which live diagram draws which upload, see the images bullet). Both comment tables **cascade** from `User` rather than `SetNull` — a version snapshot is a state of somebody else's board and outlives its author, but an authorless comment on it is worse than none at all. The schema is applied with **`prisma migrate deploy`** from `prisma/migrations/` (`npm run db:migrate:deploy`; `deploy/deploy.sh` and CI's e2e job run it). Change it with `npm run db:migrate -- --name x` and commit the generated directory; `npm run db:push` is only for a throwaway local DB. Any database created *before* migrations existed (i.e. with `db push`) must be baselined once, or `migrate deploy` tries to re-create every table: `npx prisma migrate resolve --applied 20260906065812_init` — see DEPLOYMENT.md § Database migrations. **`src/lib/diagramMigrations.ts` and the two modules under it spell out the `.js` on their relative imports**, because the server compiles and runs them under `nodenext`, where an extensionless relative import is neither a legal ESM specifier nor something Node can resolve — Vite and `tsc -b` resolve `./x.js` back to `./x.ts` on the client side.
- Persistence (**for a diagram with no document behind it** — see the collaboration bullets, which is now the usual case for a signed-in editor): `CanvasPage.tsx` subscribes to the store and autosaves with a 2 s debounce through `src/lib/autosave.ts`; unmount flushes a pending save and `pagehide` fires a keepalive save. **A failed save retries itself** — 1 s, 2 s, 4 s … capped at 30 s, unlimited while the page is open — and stays `isPending()` until one is confirmed; a new edit during a backoff falls back to the normal debounce. The autosaver's state drives `saveStatus` (`retrying` → amber in the TopBar) via `onStateChange`; `saveDiagram` never rejects (it reports through `saveStatus`), so CanvasPage translates that back into the rejection the autosaver retries on. Saved JSON is versioned — `serializeDiagram` stamps `version: CURRENT_DIAGRAM_VERSION`, and `loadDiagram` runs everything through `migrateDiagramData` (`src/lib/diagramMigrations.ts`), which upgrades unversioned v0 rows and throws on a payload from a newer build (CanvasPage shows that instead of loading, leaving autosave unarmed). Changing the shape of a diagram means a new migration step, not a silent read of the old one. **Every save is guarded**: the client keeps the `updatedAt` it loaded (then whatever each save returns, monotonically, through `noteSaved` — thumbnails write through the same `PUT` and bump it too) and sends it as `ifUnmodifiedSince`; the server compares it to the row as timestamps and answers `409 { error, updatedAt }` without writing when a second tab got there first. A 409 and a 401 are both *terminal* — `saveDiagram` returns them as outcomes rather than throwing, CanvasPage cancels the autosaver and stops scheduling, and the user is offered the TopBar's conflict banner (Reload / Overwrite, the latter resending with no guard) or `ReauthDialog`. A 401 no longer navigates from the canvas at all: `api.request` rejects with `UnauthorizedError` and `setUnauthorizedHandler` decides what else happens — the redirect to `/login` is still the default everywhere else.
- **Read-only mode is gated everywhere except the store.** `loadDiagram` takes an options bag carrying the `role` the API reported (and `shareToken`, which is only sent to an owner); `readOnly` is `role === 'viewer'`, or whatever the caller says — the public page passes `true` outright, having no role for an anonymous reader. **The store's actions are deliberately *not* gated**: they stay total, so a legitimate rewrite of a read-only board needs no bypass, and a half-applied edit is far worse to debug than one that never had a way in. What is gated: `saveDiagram` returns `'skipped'`; `CanvasPage` arms neither autosave, the thumbnail scheduler nor the image backfill; `Canvas` passes `nodesDraggable`/`nodesConnectable`/`elementsSelectable={false}`, does not render the rail, floating toolbar or text format bar, does not open the context menus, and returns early from paste, drop and the double-click that would drop a text shape; and **every mutating command is withdrawn by one predicate**, `canEditDiagram`, folded into its `when` by `gateOnEditability`. That mapping reads an **allow-list** (`READ_ONLY_COMMAND_IDS`), so a command added without being named there is gated by default. `commandDeclarations` is the ungated list, exported only so the "no two unconditional commands share a keystroke" test is not made vacuous by a `when` on everything.
- **`/s/:token` (`src/pages/SharedPage.tsx`) is the one route outside `ProtectedRoute`** — the token is the whole credential. A stored diagram points at its images as `/api/images/<id>`, which serves the owner and members only, so `src/lib/sharedView.ts` repoints every one at `/api/shared/<token>/images/<id>` as the diagram loads. The rewrite is anchored on the exact path (an inline base64 image, or a URL to another host, is left alone) and runs on the **migrated** nodes, because it has to read a shape this build understands; `loadDiagram` then migrates again, which is free. The page mounts the ordinary `Canvas` with `topBar={false}` under a slim header of its own. A revoked token and one that never existed are the same 404 and get the same page. **It opens no socket, so it polls for the two things that are about *now*:** `useLiveBoardPoll` re-reads `GET /api/shared/:token` every `SHARED_POLL_MS` (30 s — 30 requests per fifteen minutes per viewer against a route limited to 300) and writes back only `timer` and `voting`, through `useDiagramStore.setState` the way the document binding does; `src/lib/sharedPoll.ts` is the pure half (`liveBoardStateOf` narrows the payload through the same `sanitizeTimer` / `sanitizeVotingSession` gates, `liveBoardPatch` says which of the two moved, so an unchanged board costs no render). **The board itself is never re-loaded** — a `loadDiagram` would reset the viewport under a reader who has scrolled somewhere, and a shared link is a look at the drawing as it was handed over. Polling stops while the tab is hidden (`visibilitychange`) and catches up at once on the way back, and a failed poll is silent: the next one is thirty seconds away.
- **`src/components/HistoryPanel.tsx`** lists versions for every role and withholds the two writes from a viewer. "Snapshot now" flushes the pending autosave first — the server snapshots the row as it stands, so a debounced edit would be missing from the snapshot the user just asked for. Restore reloads the store from the response *and* calls `noteSaved(updatedAt)`, or the next autosave would 409 against the write the restore just made. **The preview is not React Flow**: `ConnectorEdge` looks its endpoints up in the live diagram store (that is how it routes around what is on the board), so a React Flow preview of a past version would draw that version's connectors against today's positions and nothing at all for a shape since deleted. `src/lib/versionPreview.ts` reduces a version to boxes and centre-to-centre lines in its own coordinates and lets an SVG `viewBox` scale it; `src/lib/versionHistory.ts` formats the entries by hand rather than through `toLocaleString`, so the same string comes out on every machine. **The panel also scrubs and forks** (Whimsical's history): a slider with ‹ › and Play walks the versions oldest → newest (`scrubIndex` clamps, never wraps; Play stops at the newest) by opening each one's preview, and **Fork** (`POST …/versions/:versionId/fork`, viewer+, in `server/versions.ts`) makes a new diagram of the caller's own holding that version — no history, no comments, and an image only the original's owner uploaded stays theirs (`GET /api/images/:id`'s rule) — then navigates to it.
- **Commenting is client-side in three pieces.** `src/store/useCommentStore.ts` holds the diagram's threads and the panel's own state, deliberately outside `useDiagramStore`: a comment is not part of the board, pushes no undo entry and is written straight to the server rather than through the autosave. **Every write refetches** — splicing a mutation's response into the list by hand would be a second way of being right about ordering, counts and whether deleting the last comment took the thread with it (`server/comments.ts` does exactly that). The listing is fetched as `all` and narrowed by `visibleThreads`, because the badge and the canvas pins have to know about threads the open tab is hiding. `src/lib/comments.ts` is the pure half — filtering, oldest-first pin numbering that never renumbers, the anchor's name, and a **mirror** of the server's permission rules, which exists so the panel does not offer a button that is going to 403 and is never the authority. `src/components/CommentsPanel.tsx` is the sheet (same shape as `HistoryPanel`) and `src/components/CommentPins.tsx` the numbered pins, drawn through `ViewportPortal` so they pan and zoom with the board — which also puts them inside what the image export captures, hence `.comment-pin` on `EXCLUDED_SELECTORS` in `exportImage.ts`. **Both context menus open for a signed-in viewer now**, carrying the one `comment.add` command (on `READ_ONLY_COMMAND_IDS`): writing a comment is a viewer's right. The public `/s/:token` page still gets the browser's own menu and draws no pins — `Canvas`'s `topBar` prop stands for "there is a session here", and every comment route needs a name against the remark.
- **Canvas search is ⌘F (`view.find`) over labels alone.** `src/lib/search.ts` is the whole of what "find" means — a case-insensitive substring of a shape's or a connector's label, at most one hit per element (the count is of things on the board, not of occurrences within one), ordered shapes-first in reading order (y, then x, then id) and connectors after them in diagram order. It is structural and pure like `arrange.ts`: labels and positions, never the store. `src/store/useSearchStore.ts` holds the query, the hits and the active index and cycles wrapping in both directions; it lives outside `useDiagramStore` for the reason the comment store does, and nothing in it is saved, serialized or undoable. `src/components/SearchBar.tsx` owns the two effects a hit has on the *board* — the active hit becomes the selection and the viewport moves to it (`fitView` on the shape, or on a connector's two endpoint nodes, since a connector has no box to frame) — because both need the React Flow instance and the selection is the diagram's state, not the search's. The rings are CSS: `useSearchHighlight` puts `data-search-hit="hit" | "active"` on the shape wrapper (`ShapeNode`) and on the connector's label (`ConnectorEdge`), and `[data-search-hit]` in `index.css` draws a dashed accent **outline** — outside the element's box, so a found shape keeps exactly the size, fill and stroke it was given — solid on the active one. The command is on `READ_ONLY_COMMAND_IDS`: finding something is looking, not editing, so the bar is offered on a viewer's board and on the public `/s/:token` page too.
- **Presenting is a frame per slide, and the clip is a mask in screen space.** `src/lib/presentation.ts` is the pure half — `slidesOf(nodes)` takes the frames (a nested frame is a slide of its own, as in Whimsical) and orders them: **a frame carrying `slideOrder` comes first, by that number; frames nobody has ordered follow in reading order** (y, then x, then id, in **board** coordinates through `absolutePosition`, or a nested frame would sort by an offset from its parent), so a section added to an arranged deck joins the end instead of shuffling into the middle of it. Anything that is not a finite number reads as "not ordered" — `Diagram.data` is free-form JSON. A slide carries its `rect`, its title (the label, or `Frame n` by its place in the deck) and its `background`, which is `FrameNode`'s own `color-mix` so the backdrop *is* the section's colour. `reorderSlides` returns the `updateNodeData`-shaped patches that write 0…n-1 and **nothing for a frame already carrying that number**, which is what lets the store's `setSlideOrder` be one history entry — and none at all when the order asked for is the one the board has. The running order is the one part of presenting that is *in* the diagram (everybody presents the same deck) and so is undoable; `src/store/usePresentStore.ts` holds the rest — `active` / `index`, outside `useDiagramStore` for the reason the search and comment stores are, reading the deck back out of the diagram store on every step so a frame deleted mid-talk cannot leave the index past the end, and **clamping at both ends rather than wrapping** (a deck is not a loop; ⌘F wraps because a search is). `src/components/PresentMode.tsx` is the overlay, mounted **from `Canvas`, inside the React Flow provider**: a slide change is `fitView` on that frame's node with no padding, so the slide is the board itself rather than a second renderer, and the clip is four opaque bands around the frame's box under the live `useViewport()` transform (`maskRects`, clamped to the container) — no node is touched, so a shape half out of its frame keeps its position, its parentage and its place in the export and is simply painted over. It is `absolute` inside `Canvas`'s wrapper rather than `fixed`, because the transform is relative to the flow container and the `/s/:token` page has a header above it; that header folds away while presenting, and the fit re-runs on the size change. While `active`: every piece of chrome is withdrawn (top bar, rail, both floating toolbars, bottom bar, find bar, minimap, comment pins, presence cursors, guides, all three context menus), React Flow is locked on every axis, `Canvas`'s keyboard handler stands down (the overlay takes the arrows, Space, Home/End and Escape on the **capture** phase) and **`onMoveEnd` reports nothing** — every slide is a `fitView` and the viewport is saved with the diagram, so presenting would otherwise leave the board reopening on the last slide for everybody. Exiting restores the viewport the presentation started from, and `Canvas`'s unmount stops any presentation still running. Entry points: `view.present` (⌘⇧P, gated on there being a frame) and `view.presentFromFrame` (the node menu, one selected frame, no keystroke), **both on `READ_ONLY_COMMAND_IDS`** — presenting is looking, so a viewer's board and the public page present too — plus `PresentButton` in the TopBar (and in the share page's header), whose caret opens "Arrange slides", withheld from a viewer because the order is an edit.
- **Dot voting and the board timer are shared state, so both live in the diagram — the dots as node data and the round and the countdown as board `meta`, and since `meta` joined the undo manager's scope both halves are undoable together.** The **dots are node data** (`ShapeData.votes`, voter id → count, absent on a shape nobody chose) and the **round is board meta** (`DiagramData.voting` — `{ active, dotsPerPerson, revealed, startedById }`), carried in the document's `meta` map beside `defaults` and `thumbnailNodeIds` and **read back out** for the same reason both of those are: everybody on the board votes in one round, with one budget, and the moment the totals appear has to be the same moment in every window. The **timer** (`DiagramData.timer` — `{ endsAt, startedById, label? }`) is meta too and is deliberately an **end time, never a countdown**: a "seconds remaining" would have to be written once a second by somebody, which is sixty updates a minute on the wire and one key every window fights over, where an end time is written once at the start and once at the stop and each window subtracts its own clock (`useTick` in `TimerButton.tsx` is the only per-second interval in the app, and it stops dead when there is no timer). Neither field is a format version: absent means "no round" and "no countdown", which is what every older diagram already wants, so `diagramMigrations.ts` **narrows** them (`sanitizeVotingSession` in `src/lib/voting.ts`, `sanitizeTimer` in `src/lib/timer.ts`) exactly as it narrows the defaults and the thumbnail — at all three doors, a stored row, `docToDiagramData` and the binding's `pull`. A shape's own `votes` are narrowed where they are *counted* (`votesOf`) rather than on load, because node `data` is a free-form bag everywhere else too and walking every node on every open for one field would be paid for by boards that have never been voted on. **Undo: every action here pushes** — `startVoting` / `endVoting` / `startTimer` / `stopTimer` because `meta` is inside the manager's scope now, and `toggleVote` / `removeVote` / `clearVotes` / `sortByVotes` because they touch nodes and would otherwise be folded into whatever came before. Each carries a no-op guard, so stopping a timer that is not running or closing a round that is already closed is not an entry. `clearVotes` ends the round in the same `set` and behind one `pushHistory`, so a ⌘Z brings the dots back **and** the round they were cast in. **Reaching zero chimes**, as well as flashing and reading "Time's up": `src/lib/chime.ts` generates two sine notes (~300 ms, A5 → E6) through the Web Audio API — no asset file — and `TimerButton`'s `useEndChime` plays it on the `running → done` transition seen *in this window*, guarded by `navigator.userActivation` (a browser refuses audio on a page nobody has touched) and by `useViewPreferences.timerSound`, a per-browser preference the speaker button in the timer panel writes. `playChime` takes its `AudioContext` constructor as an argument so a test can hand it something else, and every failure path is a swallowed `catch`: the flash and the label are what the sound decorates. A viewer and the public page hear it too — a countdown running out is the moment it exists for. **Who the voter is** is `DiagramState.viewerId`, set by `loadDiagram`'s options bag beside `role` and `shareToken` because it is the same kind of fact (about this reader, not this diagram); the public `/s/:token` page passes none, which is what leaves an anonymous reader with nothing to vote as. **Voting is editor+ and that is the one place this departs from commenting**: a comment has an API of its own and a viewer may write one, but a vote is diagram data and a viewer's document connection is one-way at both ends (the binding pushes nothing when `readOnly`, and Hocuspocus would refuse the update), so a dot they could place and nobody would ever see is worse than no button — a viewer still *reads* revealed totals, here and on the share page. UI: `VoteButton.tsx` and `TimerButton.tsx` in the TopBar (the share page's header mounts the timer alone, read-only), `VoteBadge.tsx` on every shape — your own dots while the round is open, the total once it is revealed, `.vote-affordance` on the two buttons so `exportImage.ts` leaves them out while the counts stay in. `src/lib/voting.ts` is the pure half (counting, the budget, `sortedByVotes`, and `voteRowPositions`, which lays a row from the group's own bounding-box corner the way `applyLayout` does so the drawing never jumps) and `src/lib/timer.ts` the other (`remainingSeconds`, `formatRemaining`, `timerState`). Neither has a keystroke or a command: opening a round is a rare, deliberate act and the letters left are worth more elsewhere.
- View preferences (minimap, grid snapping, the theme, and `timerSound` — whether the board timer chimes) are per-browser, not per-diagram: `src/store/useViewPreferences.ts` holds them and writes each change through `src/lib/preferences.ts`, a deliberately forgiving `localStorage` wrapper (blocked storage, a full quota and a value of the wrong type all fall back to the caller's default). Nothing here reaches `DiagramData`, a save or the undo history.
- **Theming is two layers of CSS variables and no React.** `src/index.css` defines the runtime tokens (`--canvas`, `--panel`, `--field`, `--ink-900…600`, `--line*`, `--hover*`, `--minimap-*`, `--danger-*`, `--warn-*`) on `:root` for light and redefines them twice for dark — once under `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) }` and once under `:root[data-theme="dark"]`. A second `@theme inline` block maps `--color-*` onto them, so `bg-panel` / `text-ink-700` / `ring-line` compile to `var(--panel)` and a theme change repaints without a rebuild or a re-render; **anything reaching for a themed token outside a utility must use the runtime name (`var(--canvas)`), not `var(--color-canvas)`**, which `@theme inline` does not emit. `src/lib/theme.ts` is the whole decision: `resolveTheme(pref, systemDark)` is pure and tested, `applyTheme` is the thin DOM wrapper that stamps `data-theme` for an explicit choice and **removes** it for `'system'` — that absence is what leaves the media query in charge, so the OS is followed live with nothing listening. What does *not* move with the theme: `--color-ink-950` and the accents (the rail, floating toolbars, menus and tooltips are dark chrome in both themes), and `--color-shape-ink` (a shape's label, whose contrast is decided by the user's fill through `isDarkFill`). **Shapes, connectors and fills are user data and render identically in both themes** — a white shape on a dark board is correct. The canvas is Whimsical's board grey (`--canvas: #eaeff4` light, `#0f171f` dark), which is what lets a filled shape wear **no outline and no shadow** and still stand out; the palette (`src/lib/palette.ts`) is Whimsical's eleven theme hues plus a neutral column, each mixed into four tiers, so the two apps' boards sit in one family. Exports go further: `captureDiagram` pins `data-theme="light"` for the capture through `pinLightTheme` and restores exactly what was there, so a dark-mode user's PNG/SVG is not dark. **Every export option is a `CaptureOptions` field** (`src/lib/exportImage.ts`): `pixelRatio` 1 or 2, `background` a colour or `null` for transparent, and `selectionOnly`, which `exportSubset` (pure, tested) turns into the selected nodes with their subtrees, the connectors joining two of them, and bounds computed through `boardRect` so a framed child is framed where it really is — an export with nothing selected is the whole board, so the Export menu passes the preference through unchecked. `nodeIds` is the same subset asked for by id rather than by selection (the board's custom thumbnail) and **overrides** `selectionOnly`; an id naming nothing is ignored, and a set with nothing left in it draws nothing — an explicit ask for two deleted shapes is not an ask for everything, so the fallback to the whole board is the caller's. `⌘⇧C` (`clipboard.copyAsImage`) is that with `{ selectionOnly: true, background: null }`, which is what Whimsical's Copy as PNG does.
- Images: `server/images.ts` (`/api/images`, raw `image/*` up to 10 MB) writes bytes to `UPLOAD_DIR/<userId>/<id>.<ext>` and rows the metadata in `Image`; `server/imageTypes.ts` sniffs magic bytes (never the Content-Type); `server/imageRefs.ts` is the pure scanner (`imageIdsInDiagram`) and `deleteOrphanImages` garbage-collects: deleting a diagram, **and any `PUT /api/diagrams/:id` that drops an image from `data`**, deletes the images nothing of the owner's still references (the collection runs after the row is written and after the index is synced, or the pre-edit state would count as a live reference). **"Nothing" means live diagrams *and* stored `DiagramVersion` rows**; an image kept only by history survives, and the moment it stops being kept is when retention prunes that snapshot (see `versions.ts`). **`server/diagramImages.ts` and the `DiagramImage` join table are how "does anything still point at this image?" is answered** — a row per (diagram, image) pair, written by `syncDiagramImages` on every write that changes `data` (create/import, PUT, duplicate, restore) and cascaded away with either side. It replaced three scans that each read the JSON of every diagram in scope: `memberCanSeeImage`, the shared-token image route and the GC's survivor check are all one indexed lookup now. **Only live diagrams are indexed** — versions are still scanned, but only for a candidate no live diagram claims, so that scan runs when an image is already up for collection rather than on every request. A sync failure is logged and **holds the collector back** (a stale index is a reason to keep an image, never to delete one). An existing database is backfilled once by `scripts/reindex-images.ts` (DEPLOYMENT.md § Backfilling the image index) — deliberately a one-off rather than a lazy backfill on a read path, which would reintroduce exactly the scan being removed and could not help the GC, whose question is about *other* diagrams. JSON body limit is 5 MB, which is why a diagram stores the `/api/images/<id>` URL and never the bytes. Client side: paste, drop and the rail's picker all go through `src/lib/useImageInsert.ts` → `src/lib/imageUpload.ts` (downscale to 2000 px, upload, then swap the URL into the "Uploading…" placeholder node). Nodes of `shape: 'image'` render as the bare `<img>`; **rectangles carrying a base64 `data.imageSrc` are the pre-upload format and must keep rendering** — old diagrams still hold them, and `src/lib/imageBackfill.ts` quietly moves them out: CanvasPage runs it after the load (never blocking it), each inline image is uploaded, and `applyImageBackfill` repoints the node with **no** history entry, leaving the normal autosave to persist it. A failed upload leaves that node inline for the next open.
- **`server/collab.ts` is the realtime server** — Hocuspocus (Yjs), **attached** to the Express `http.Server` rather than given a port of its own: `index.ts` builds the server with `http.createServer(app)` (not `app.listen`, which keeps the `upgrade` event to itself) and `attachCollab(server)` routes `upgrade` requests on **`/collab`** through a `noServer` `ws` `WebSocketServer` into `hocuspocus.handleConnection`. Any other upgrade path is destroyed rather than left half-open. In Hocuspocus 4 `handleConnection` does *not* subscribe to the socket — it returns a `ClientConnection` that has to be fed `handleMessage`/`handleClose` by hand — and it speaks the web `Request`, so the Node `IncomingMessage` is converted. **Auth is the cookie, not a token**: the socket is same-origin with the API, so `onAuthenticate` reads the session with `auth.api.getSession` off the upgrade headers exactly as `requireAuth` does, parses `diagram:<id>` out of the document name, resolves the role with `getDiagramAccess`, rejects no-session / no-access / an unrecognised document name, and sets `connectionConfig.readOnly` for a `viewer` (connected, not refused — presence is a viewer's right). Vite's dev proxy forwards `/collab` alongside `/api`; production is one process serving both. **The `Y.Doc` is the diagram**, from phase 2 on — see the next two bullets.
- **The open diagram lives in the `Y.Doc`, and `Diagram.data` is a snapshot rendered from it.** `shared/collabDoc.ts` is the format both ends agree on: `nodes` and `edges` are `Y.Map`s with **one entry per element, keyed by its own id** — which is what makes two people editing different shapes a merge rather than a conflict — and each entry carries the element's `order`, because a `Y.Map` has none and a diagram's node array *is* its z-order as well as its parents-before-children invariant. A z-order command therefore rewrites the entries that moved past each other and nothing else, where a single shared array of ids would be one key every edit fought over. `meta` holds five things and they are read back on opposite rules — and are undone on those same opposite rules, since `meta` is in the undo manager's scope and the viewport is excluded from it by writing under a second, untracked transaction origin (see the undo bullet). The viewport is written for the snapshot's sake and deliberately **never read back** — a peer scrolling their window must not move yours — while the board's `defaults` (⌘⇧D, see that bullet), its `thumbnailNodeIds` (`THUMBNAIL_KEY`, "Set as board thumbnail") and its `voting` / `timer` (`VOTING_KEY` / `TIMER_KEY`, see the voting bullet) **are**, because all four are properties of the board rather than of the window they were set in: the dashboard card is the same card for everybody, and so is the round everybody is voting in. `server/collab/render.ts` is the only place a document becomes JSON (`docToDiagramData`, always stamped `CURRENT_DIAGRAM_VERSION`) or JSON becomes a document (`seedDocFromDiagramData`, which runs `migrateDiagramData` first). **Lazy upgrade:** a diagram gets a `DiagramDoc` row the first time somebody opens it collaboratively — `fetch` seeds the document from `Diagram.data` and writes the state back at once — and never before; nothing is bulk-migrated. Hocuspocus's `store` hook (debounced 2 s / 10 s, the cadence the JSON autosave ran at) then does the four writes one `PUT` used to: the document, the rendered snapshot, `recordVersionIfDue` on the usual interval, and `syncDiagramImages` + the orphan collector, the last three best-effort for the same reason they are in the `PUT` handler. **The snapshot is behind the document by that debounce**, which is fine for everything that reads a board to draw it and wrong for the one feature that freezes a board on purpose: `server/collab/live.ts` is a registry (`attachCollab` registers, `versions.ts` asks — the import cannot point the other way, since `collab.ts` already imports `versions.ts`) that answers "what does the open document actually say?", and both a manual "Snapshot now" and the `Before restore` entry go through it rather than through the row.
- **The invariant: nothing writes `Diagram.data` but the snapshot renderer, and it is tested.** `server/dataInvariant.test.ts` scans the server sources with a bracket matcher (a regex cannot tell `data: { data }` from `data: { title }`) and fails if any module but `collab.ts`, `router.ts` and `versions.ts` writes the column. **`PUT /api/diagrams/:id` refuses a `data` write to a diagram that has a `DiagramDoc` row** — `409`, which is what a pre-realtime tab's conflict banner already knows how to recover from — while the rename, the star, the thumbnail and the folder keep working, so the lookup is only made when `data` is really being written. Import creates a diagram nobody has open (seeded on its first open, so nothing special is needed); a version restore writes JSON server-side and the client re-seeds the document through the same `loadDiagram` every open goes through, which the binding sees as one edit.
- **`src/lib/collab/binding.ts` ties the document to the store, and does it by diffing rather than by hooking every action.** Every mutating action ends in one synchronous `set`, so one store subscription is exactly one `doc.transact` per action — and what it compares is the *serialized* diagram, so a selection change, a measured size or a re-rendered array that leaves the saved JSON identical writes nothing at all. Coming the other way it rebuilds the arrays through `setState` (so a collaborator's edit is not in your undo stack) and merges back the fields that belong to this browser alone: `selected`, `measured`, `dragging`. **Gestures are committed, not streamed:** the store carries a `transientSeq` that every per-frame write bumps (the transient actions, and `onNodesChange` while a drag or resize is still in flight), and the binding holds those until the gesture stops moving — *held*, not dropped, because a text shape growing under the keyboard never commits, so the trailing flush is what guarantees its last frame is written. `useCollabStore` owns the lifecycle: it binds after the provider's `synced` (the document is the source of truth, so binding before it arrived would empty the canvas), one-way for a viewer, and registers `setDocumentFlush` on the diagram store.
- **For a collaborative diagram `saveDiagram` sends nothing, and from phase 3 nothing calls it on a timer either.** The document *is* the save, so there is no body and no `ifUnmodifiedSince` — the conflict a second tab used to be refused for is a merge now, and the banner cannot trigger. `CanvasPage` therefore arms the autosave effect (debounce, retry backoff, `pagehide` keepalive, conflict/unauthorized stand-down) **only while `useCollabStore.bound` is false**, and the thumbnail scheduler + image backfill live in an effect of their own that runs either way — a picture of the board goes through the same `PUT` and no socket produces one. **That picture is the whole board unless `DiagramData.thumbnailNodeIds` says otherwise** ("Set as board thumbnail" / "Remove from board thumbnail", `view.setThumbnail` / `view.clearThumbnail`, both edits): the ids round-trip exactly the way `defaults` does — narrowed at every door by `sanitizeThumbnailIds` (`src/lib/boardThumbnail.ts`), carried in the document's `meta`, absent on a board with the automatic card — and the scheduler passes what is left of them as `CaptureOptions.nodeIds`. **Ids naming deleted shapes are ignored but never pruned** (an undo or a restore brings the shape back), and with none of them left the card falls back to the whole board; a change to the ids is captured at once rather than within the 30 s interval, since it is a command the user just ran. Setting one **is** undoable, for the reason `saveSelectionAsDefault` is — `meta` is in the undo manager's scope — and re-setting the same ids costs nothing. Nothing was deleted: an unbound diagram (no session on the socket, a proxy that will not upgrade, an older deployment) is still kept entirely by that loop, and `saveDiagram`'s document branch is still what `HistoryPanel`'s "Snapshot now" and the unmount flush go through.
- **The save indicator is a connection indicator for a bound diagram.** `src/lib/collab/connectionStatus.ts` is the whole mapping (`connecting` → "Reconnecting…" amber, `connected` → "Live" green, `disconnected` → "Offline — changes will sync when you're back" red), and `TopBar` picks between `LiveIndicator` and the legacy `SaveIndicator` on `bound` (a viewer still gets `ViewOnlyPill`). `useCollabStore.synced` is the *other* question — "has what I did left this window?" — which needs the provider (`isSynced && !hasUnsyncedChanges`) **and** the binding, since a gesture is held in `binding.ts` for 150 ms before the provider is offered it at all. It is not shown (the label says "Live" either way) but it rides on the element as `data-collab-sync`, which is what the e2e suite waits on where it used to wait on "Saved" — `expectSynced` in `e2e/diagram.spec.ts`.
- **The document is cached in the browser too, and the cache is what binds first.** `src/lib/collab/offline.ts` wraps `y-indexeddb` (one database per diagram, `flowsketch:diagram:<id>`); `useCollabStore` attaches it alongside the provider and binds the store to the document on **whichever of the two first puts a real diagram in it** — IndexedDB nearly always, so a board opened here before draws without waiting for a round trip and the server's state merges in when it lands. **An empty cache is not a document**: binding to one would draw a blank canvas over the board the page already loaded over HTTP, so a first open on this machine still waits for the provider. Every failure mode — no IndexedDB, a private window that throws, a store that cannot be read — returns `null` and the diagram is simply the one phase 3 shipped; a board is worth more than a copy of it. The public `/s/:token` page never opens a connection at all, so it caches nothing.
- **A refused socket says which refusal it is, and the browser acts on it.** Hocuspocus would otherwise answer every rejected `onAuthenticate` with a `permission-denied` that says nothing, which is not enough to decide between two opposite actions. `shared/collabAuth.ts` holds the two strings the server throws (`CollabAuthError` in `server/collab.ts`) and `src/lib/collab/authFailure.ts` reads them: `unauthorized` → `useCollabStore.authFailed`, which `CanvasPage` shows the **same** `ReauthDialog` for as a refused `PUT` (`saveStatus === 'unauthorized'`); `forbidden` → `accessLost`, which is a toast and a trip to the dashboard, *and* `IndexeddbPersistence.clearData()` — a cached copy of somebody's diagram must not outlive their access to it. Anything unrecognised is `unknown` and does nothing. **Signing back in replaces the socket** (`PresenceConnection.reconnect`) rather than nudging it: auth here is the cookie on the *upgrade request*, so the refused connection is holding the session that expired. Hocuspocus refuses with a message rather than a close, so that socket is usually still open and the websocket provider will not `connect` while it thinks so — `reconnect` closes it and waits for the close before reopening.
- **Presence is Yjs awareness, and lives outside `useDiagramStore`.** `src/lib/collab/presence.ts` owns the `HocuspocusProvider` and the pure half (`peerColor`, `peersFrom`, `throttle`, `collabUrl`, `initialsOf`); `src/store/useCollabStore.ts` holds `peers` / `status` for the UI. Awareness state is flat and exactly `{ userId, name, color, cursor: {x,y} | null, selection: string[] }` — `cursor` in **flow coordinates**, throttled to ~30/s, `null` when the pointer leaves; `selection` mirrored off the diagram store by subscription rather than pushed by the dozen actions that can change it. The colour is derived from the user id (a djb2 hash into an 8-colour palette), so it is the same in every window and survives a reconnect. Peers are kept out of the diagram store deliberately: they change tens of times a second and would otherwise run autosave, history and every canvas selector on somebody else's gesture. Nothing security-relevant may be read from an awareness state — it is written by another browser. Rendering is `PresenceCursors.tsx` (a `ViewportPortal`, like comment pins, so cursors pan and zoom with the board — hence `.presence-cursor` on the export exclusion list in `exportImage.ts`), `data-peer-selected` + `--peer-color` on `ShapeNode`/`FrameNode` (the search-hit pattern), and `PresenceStrip.tsx` in the TopBar. `CanvasPage` connects and disconnects; the public `/s/:token` page never mounts it.

## Conventions

- **Every store action that mutates nodes/edges must `pushHistory` first — it is now the undo *boundary*, not just a snapshot.** For a diagram with no document behind it, it pushes onto `past` as it always did; for one bound to a Yjs document it tells the `Y.UndoManager` that the next edit starts a new step. Get it wrong in the second case and the edit is silently folded into the one before it, so ⌘Z takes back two things. The deliberate exceptions are unchanged and stay documented at their call sites: the transient actions (one gesture is one step), and the housekeeping that is not the user's edit to take back (`applyImageBackfill`, the image placeholder resolution). **The board's `meta` is not an exception any more.** `saveSelectionAsDefault`, `setThumbnailNodeIds`, `startVoting` / `endVoting`, `startTimer` / `stopTimer` and `clearVotes` all push, because the document's `meta` map is inside the `Y.UndoManager`'s scope (see the undo bullet: only the viewport is kept out, by origin) and the snapshot `Snapshot` carries `defaults` / `thumbnailNodeIds` / `voting` / `timer` so the unbound history says the same thing. What each of them adds is a **no-op guard** rather than an exception — re-setting the same thumbnail, closing an already-closed round or stopping a timer that is not there costs no ⌘Z. `lastStyle` is in neither history: it is this tab's habit, not the board's state. The rule cuts the other way too, and `pasteMermaid` is the one place that leans on it: **a boundary is what starts an entry, not a `set`**, so two writes either side of an `await` are one ⌘Z as long as only the first was preceded by a `pushHistory` — which is why that action composes the layout itself instead of calling `layoutSelected`.
- `src/lib/defaults.ts` owns the default edge style: `DEFAULT_EDGE_STROKE`, `DEFAULT_STROKE_WIDTH` / `CONNECTOR_STROKE_PX`, `DEFAULT_START_ARROW` / `DEFAULT_END_ARROW`, and `makeEdgeData(connectorType)`. Build a new connector's `data` with the factory; never re-inline the hex (it is spelled out in exactly one place). The optional fields (`strokeWidth`, both arrow styles) are absent on older diagrams, so read them through those defaults — that is what keeps an old connector drawn exactly as it was.
- Tests: pure logic next to the file (`*.test.ts`), store tests drive `getState()`, API tests mock `./db.js` and `./middleware.js` with `vi.mock`, user flows in `e2e/`. Bug fixes start with a failing test; `it.fails` marks a documented known bug.
- **Supertest suites talk to a server from `server/testServer.ts`, never to a bare app.** `listen(0)` with no host binds the IPv6 wildcard `::`, which on macOS can hold the *same port* as an IPv4 `0.0.0.0` socket elsewhere — a connection to `127.0.0.1:<port>` then lands on whichever the kernel prefers, not necessarily the one that reported that port. `request(app)` made supertest bind and immediately close such a server per *request* (~150 draws a run across eight workers), so about one run in twenty answered some assertion from another test file's app (`images.test.ts`'s auth gate returning `403`, which no image route produces), or hung to the 5 s timeout, or `ECONNRESET`. `serveForFile(app)` at module scope — `serveForTest(app)` for the suites that must build an app per case — binds `127.0.0.1` explicitly and holds one port. That was the whole of the "flaky auth gate": not `authState`, not a missing `await`. Don't chase a wrong-status flake in a supertest file into the auth mock.
- Don't loosen a test to make it pass. If a router/geometry assertion fails, the tolerance is documented in the test — investigate before changing it.
